# Update Project Documentation

## 1. Map the change to the doc(s) it affects

| Change | Doc(s) to update |
| --- | --- |
| Environment variable added/removed/changed | `docs/administrator-guide.md` - Environment variables table |
| New Processor / Controller Service / Reporting Task, or a property added to an existing one | `docs/user-guide.md` (regenerated - see below); exclude test-only artifacts via `docs/template/documentGeneratorConfig.yaml` instead of hand-editing the generated tables |
| New extension point, volume/directory, logging or NiFi-config mechanism, cluster-config option | `docs/administrator-guide.md` - matching section |
| New installation/deployment step or prerequisite | `docs/installation-guide.md` |
| New tool, child module, or capability listed in the top-level bullets | `README.md` (Overview/Tools section) and, for a new tool, its own `<module>/README.md` plus the `qubership-nifi-tools/README.md` tool list |

A single change can touch more than one row - e.g. a new processor that also
introduces a controlling environment variable needs both the regenerated user
guide and the administrator guide table.

A single new Processor/Controller Service/Reporting Task does not need a
matching bullet in root `README.md`'s Overview section - that list enumerates
capability *categories* (bulk DB operations, rules-based validation, etc.),
not individual components, and would grow unreadable if it tracked every
component. Only touch it when the change introduces a genuinely new category.

## 2. Regenerating docs/user-guide.md

Everything between the `<!-- ... DO NOT REMOVE -->` marker comments is
generated by the `qubership-nifi-docs-generator` Maven plugin from the
component's `@CapabilityDescription`/`@Tags` annotations and its
`PropertyDescriptor` definitions. Never hand-edit that text - it is
overwritten on the next generator run and will drift from the code. After
adding, removing, or changing a Processor/Controller Service/Reporting Task
or its properties, regenerate from the repository root:

```bash
mvn clean install -DskipUnitTests=true   # build once so the plugin can discover the NAR/JARs; skip if already built
mvn org.qubership.nifi:qubership-nifi-docs-generator:generate
```

Only the text outside the markers, in `docs/template/user-guide-template.md`,
is hand-authored (section intros, prerequisites). Edit that file directly,
then regenerate so the change flows into `docs/user-guide.md`.

If a new component's artifact should not appear in the guide at all (test-only
bundles, etc.), add it to `excludedArtifacts` in
`docs/template/documentGeneratorConfig.yaml` rather than deleting rows from
the generated output by hand.

## 3. Environment variables table (administrator-guide.md)

The table uses four columns: `Parameter | Required | Default | Description`.

- `Required` is `Y`, `N`, or a condition mirroring existing conditional rows,
  e.g. `Y (if AUTH = oidc)` or `Y (if NIFI_CLUSTER_IS_NODE = true)`.
- Insert the new row next to the variables it relates to (e.g. all
  `AUTH`-dependent variables are consecutive, all `ZOOKEEPER_*` variables are
  consecutive) instead of appending at the end - the table is organized by
  feature area, not alphabetically.
- Wrap literal values and enumerations in backticks, matching the existing
  rows.

## 4. `README.md` consistency

Root `README.md` lists each `qubership-nifi-tools` child module as a bullet
under "Tools", linking to `qubership-nifi-tools/README.md`. When adding a new
tool module:

1. Add its own `README.md` under the module directory.
2. Add a bullet for it in `qubership-nifi-tools/README.md`.
3. Add a one-line bullet for it in the root `README.md` "Tools" section if the
   tool is user-facing (skip internal-only helper/test modules).

For any other significant capability (new auth mode, new cluster mechanism,
etc.), check whether the root `README.md` "Overview" bullets need a matching
update.

## 5. Before finishing

Confirm every doc edit matches the code change exactly - no leftover
references to a removed variable, no missing entry for a new one. Don't
invoke the `lint` skill or the `/lint` prompt yourself: this repository
already runs its linters automatically as a `PostToolUse` hook on every file
you write or edit, and `/lint` is a manual, user-invoked command.
